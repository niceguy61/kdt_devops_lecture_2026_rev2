# 7교시 · 처음부터 보안 — DevSecOps와 비밀값

> [!NOTE]
> **이번 시간에 할 일**
>
> - 보안을 **마지막 검사**가 아니라 **흐름 전체에 나눠 넣는** 이유를 압니다(DevSecOps).
> - 비밀값(비밀번호 · 토큰 · 열쇠)이 **어떻게 새는지**, 새면 왜 "지우기"로 끝나지 않는지 압니다.
> - 내가 쓰는 남의 코드(의존성 · 이미지)도 공격 경로가 된다는 것을 사례로 압니다(공급망).
> - 5주 동안 어떤 보안 장치를 **어느 단계에** 하나씩 넣게 되는지 지도를 봅니다.

## 보안을 왜 '처음부터' 하나

2교시의 SDLC를 떠올리면, 예전에는 개발이 다 끝난 뒤 보안 팀이 **마지막 관문**에서 검사했습니다. 그 방식은 두 가지 문제가 있습니다.

| 마지막에 몰아서 검사하면 | 결과 |
|---|---|
| 문제를 늦게 찾는다 | 설계부터 다시 해야 해서 고치는 비용이 크다 |
| 배포가 하루 수십 번이면 | 관문 앞에 줄이 서서 **보안이 병목**이 된다 (1교시 DevOps의 벽 그대로) |

**DevSecOps**는 보안 점검을 SDLC의 **각 단계에 자동으로 나눠 넣는** 방식입니다. 커밋할 때, CI가 돌 때, 이미지를 만들 때, 배포할 때, 운영할 때 — 각자 작은 검사를 합니다. 흐름의 **왼쪽(앞쪽)으로 옮긴다**고 해서 **시프트 레프트(shift left)**라고도 부릅니다.

> **🧩 비유 — 공항 보안**
>
> 탑승구 앞에서 한 번에 모든 것을 검사하면 비행기가 늦습니다. 그래서 공항은 **예약할 때 신원**, **체크인할 때 짐**, **보안 검색대에서 몸**, **탑승구에서 표**를 각각 짧게 확인합니다. 하나가 뚫려도 다음 단계가 막아 줍니다(**다층 방어**).

## 비밀값은 어떻게 새나

비밀값(secret)은 **아는 사람이 곧 주인이 되는 값**입니다. 비밀번호, API 토큰, 클라우드 Access Key, DB 접속 정보, 인증서의 개인 열쇠가 모두 해당합니다.

| 새는 경로 | 실제 모습 |
|---|---|
| **코드에 직접 적기** | `DB_PASSWORD = "devmart123"`을 소스에 넣고 GitHub에 push |
| 설정 파일을 같이 올리기 | `.env`, `credentials.json`을 `git add .`로 함께 커밋 |
| 로그에 찍기 | 디버깅하려고 요청 헤더 전체를 로그에 출력 → `Authorization: Bearer …` |
| 화면 공유 · 스크린샷 | 1일차에 약속한 그것 |
| 이미지 안에 남기기 | Dockerfile에서 비밀값을 복사한 뒤 지워도 **이전 레이어**에 남는다 (2주차 3일차) |

> [!WARNING]
> **지워도 끝나지 않는다**
>
> 비밀값을 커밋했다가 다음 커밋에서 지워도 **Git 기록(history)에는 그대로 남습니다.** 공개 저장소라면 push한 순간 자동 수집 봇이 몇 분 안에 가져갈 수 있습니다. 그래서 새어 나간 비밀값의 처리 순서는 항상 같습니다.
>
> 1. **먼저 무효화** — 그 비밀번호를 바꾸고, 그 토큰 · 열쇠를 폐기합니다.
> 2. 그다음 기록에서 지우고, 어디에 쓰였는지 확인합니다.
>
> 순서를 바꾸면, 기록을 지우는 동안 이미 가져간 사람이 그 열쇠를 씁니다.

### 그래서 이렇게 한다 (2주차부터 실습)

| 습관 | 어떻게 |
|---|---|
| 비밀값은 코드 밖에 | **환경 변수**나 비밀값 저장소에서 읽는다 (2주차 4일차 · 3주차 Secret · 5주차 AWS) |
| 올리지 않을 파일은 처음부터 막기 | `.gitignore`에 `.env` 등록, 예시는 `.env.example`로 (2주차 4일차) |
| 올리기 전에 기계가 한 번 더 | GitHub는 공개 저장소에 **push 보호**를 켜 두어, 알려진 형식의 토큰이 들어 있으면 push를 막는다 |
| 오래 사는 열쇠를 줄이기 | 짧게 사는 토큰 · 역할로 (4일차 8교시, 5주차 OIDC) |

## 남의 코드도 내 코드다 — 공급망

DevMart의 코드는 수백 줄이지만, 함께 딸려 오는 **라이브러리 · 베이스 이미지 · 도구**는 수백만 줄입니다. 이 중 하나가 오염되면 내 코드가 아무리 깨끗해도 소용없습니다. 물건이 공장에서 가게까지 오는 길에 비유해 **소프트웨어 공급망(software supply chain)**이라고 부릅니다.

| 사건 | 무슨 일 | 교훈 |
|---|---|---|
| **Log4Shell** (2021.12) | 자바 로그 라이브러리 Log4j에 원격 실행 취약점. 수많은 서비스가 이 라이브러리를 **쓰는 줄도 모르고** 썼다 | **무엇을 쓰고 있는지 목록(SBOM)**이 있어야 빨리 찾는다 |
| **SolarWinds** (2020) | 관리 도구의 **빌드 과정**에 악성 코드가 심겨, 정식 업데이트로 고객 수천 곳에 배포 | 빌드 과정과 결과물에 **서명 · 증명**이 필요 |
| **xz utils** (2024.3) | 압축 라이브러리에 2년에 걸쳐 신뢰를 쌓은 기여자가 **백도어**를 심음. 한 엔지니어가 SSH 로그인이 0.5초 느려진 것을 수상히 여겨 발견 | 오픈소스 유지보수자의 부담, **이상한 숫자를 그냥 넘기지 않는 습관**(2일차 8교시) |

## 5주 동안 넣을 보안 장치 지도

| 단계 | 장치 | 언제 실습 |
|---|---|---|
| 계정 | MFA, 최소 권한 | 2주차 1일차 GitHub 2FA · 5주차 AWS 루트 MFA · IAM |
| 코드 | `.gitignore`, push 보호, 리뷰 | 2주차 |
| 빌드 | 작은 베이스 이미지, **취약점 스캔 · SBOM** | 2주차 3일차 |
| CI | 테스트 통과 · 리뷰 없이 main에 못 들어가게, 토큰 권한 최소화 | 3주차 2일차 |
| 배포 | 이미지 **서명**과 검증, 정책 엔진 | 4주차 5일차 |
| 실행 | RBAC, ServiceAccount, 서비스 간 **mTLS** | 4주차 4~5일차 |
| 클라우드 | 보안 그룹, IAM 역할, 감사 기록(CloudTrail) | 5주차 |

> [!IMPORTANT]
> **보안 장치는 하나씩, 매일**
>
> 5주 뒤에 "보안 주간"이 따로 있는 게 아닙니다. 위 표처럼 **매주 그 주에 만든 것에 맞는 보안을 하나씩** 붙입니다. 그것이 DevSecOps입니다.

> **🎓 학술 노트 — 「신뢰를 신뢰하는 것에 대하여」 (Thompson, 1984)**
>
> 유닉스를 만든 **켄 톰프슨(Ken Thompson)**은 1983년 튜링상 수상 강연에서 섬뜩한 실험을 소개했습니다. **컴파일러**(코드를 실행 파일로 바꾸는 프로그램)를 조작해, 로그인 프로그램을 컴파일할 때 몰래 뒷문을 넣게 하고, 컴파일러 자신을 컴파일할 때도 그 조작을 다시 심게 만든 것입니다. 이렇게 하면 **소스 코드를 아무리 꼼꼼히 읽어도 뒷문이 보이지 않습니다.** 그의 결론은 "직접 만들지 않은 코드는 완전히 믿을 수 없다"였습니다.
>
> 40년 뒤 SolarWinds와 xz 사건은 이 경고가 현실이 된 사례입니다. 그래서 오늘날 공급망 보안은 "믿는다"가 아니라 **"누가, 어떻게 만들었는지 증명을 남기고 확인한다"**(SLSA, 서명, SBOM)는 쪽으로 가고 있습니다. 4주차 5일차 7교시에 직접 서명하고 검증해 봅니다.
>
> - Thompson, K. (1984). Reflections on trusting trust. *Communications of the ACM*, 27(8), 761–763.

> **📈 트렌드 — 보안이 '권장'에서 '의무'로**
>
> 유럽연합의 **사이버 복원력법(Cyber Resilience Act, CRA)**은 2024년 12월 발효되어, **2026년 9월부터** 디지털 제품 제조사에게 악용 중인 취약점과 중대 사고를 정해진 기한 안에 보고할 의무를 지웁니다. 미국 정부도 공급 업체에 **SBOM**과 안전한 개발 절차 증명을 요구하고 있습니다. 비밀값 유출도 줄지 않아서, 보안 기업 GitGuardian은 2024년 한 해 공개 GitHub에 새로 노출된 비밀값이 **2천만 개를 넘었다**고 보고했습니다. 그래서 기업은 신입 DevOps 엔지니어에게도 "보안 도구를 파이프라인에 넣을 줄 아는가"를 묻습니다.

## 정리

- **DevSecOps**는 보안을 마지막 관문이 아니라 **각 단계의 작은 자동 검사**로 나눠 넣는 방식입니다(시프트 레프트, 다층 방어).
- 비밀값은 **코드 · 설정 파일 · 로그 · 이미지 레이어**로 샙니다. 새면 **먼저 무효화**하고, 그다음 지웁니다.
- 내가 가져다 쓰는 라이브러리 · 이미지도 공격 경로입니다(공급망). **목록(SBOM)과 서명**으로 대응합니다.
- 5주 동안 매주 그 주에 만든 것에 맞는 보안 장치를 하나씩 붙입니다.

> **✅ 확인 문제**
>
> 1. AWS Access Key를 실수로 공개 저장소에 push했습니다. 가장 먼저 할 일은?
> 2. Dockerfile에서 비밀 파일을 `COPY`한 뒤 다음 줄에서 `rm`했습니다. 안전한가요?
> 3. Log4Shell 때 "우리 서비스가 Log4j를 쓰는지"를 빨리 답하게 해 주는 것은?
> 4. 보안 점검을 SDLC 앞쪽 단계로 옮기는 것을 무엇이라 부르나요?
> 5. 「신뢰를 신뢰하는 것에 대하여」가 보여 준 위험은 무엇인가요?
>
> <details><summary>정답</summary>
>
> 1. 그 키를 즉시 비활성화 · 삭제(무효화)하는 것. 기록 정리는 그다음입니다.
> 2. 아닙니다. 이전 레이어에 파일이 남아 이미지를 받은 누구나 꺼낼 수 있습니다.
> 3. SBOM(소프트웨어 구성 목록)
> 4. 시프트 레프트(shift left)
> 5. 소스 코드를 읽어도 보이지 않는 뒷문이 빌드 도구를 통해 들어올 수 있다 — 직접 만들지 않은 코드는 완전히 믿을 수 없다.
>
> </details>
