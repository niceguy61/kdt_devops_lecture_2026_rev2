# 8교시 · API와 인증 — 누구인가, 무엇을 해도 되나

> [!NOTE]
> **이번 시간에 할 일**
>
> - **인증**(누구인가)과 **인가**(무엇을 해도 되나)를 구분합니다.
> - **세션**과 **토큰** 방식이 상태를 어디에 두는지 비교합니다.
> - JWT 한 개를 세 부분으로 나눠 읽고, "서명"이 무엇을 보장하는지 압니다.
> - OAuth 2.0 · OIDC가 "GitHub로 로그인"을 어떻게 가능하게 하는지, 이 과정의 어디서 다시 만나는지 압니다.
> - 다시 보내도 안전한 API(멱등성)와 429 응답의 뜻을 압니다.

## 두 가지 질문 — 인증과 인가

| | 인증 (Authentication, AuthN) | 인가 (Authorization, AuthZ) |
|---|---|---|
| 질문 | **너는 누구냐?** | **너는 이것을 해도 되나?** |
| 수단 | 비밀번호, 일회용 코드(MFA), 인증서, 토큰 | 역할(role), 정책(policy), 권한 목록 |
| 실패하면 | **401** Unauthorized | **403** Forbidden |
| 비유 | 건물 입구에서 **신분증 확인** | 출입증에 찍힌 **층 · 방 권한** |

> [!TIP]
> **401과 403을 헷갈리지 않는 법**
>
> 401은 "누군지 모르겠다 → 다시 로그인하라", 403은 "누군지는 안다 → 그래도 안 된다"입니다. 5주차 AWS에서 `AccessDenied`(403 계열)를 만나면 **로그인을 다시 하는 게 아니라 권한(정책)을 고쳐야** 합니다.

## 로그인 상태는 어디에 두나 — 세션과 토큰

2교시에서 "서버는 상태를 갖지 않아야(stateless) 늘리기 쉽다"고 했습니다. 그런데 로그인은 **상태**입니다. 그 상태를 어디에 두느냐로 두 방식이 갈립니다.

| | 세션 방식 | 토큰 방식 (JWT) |
|---|---|---|
| 로그인 후 서버가 주는 것 | 의미 없는 **번호표**(세션 ID)를 쿠키로 | 내용이 적힌 **서명된 증명서**(토큰) |
| 상태를 기억하는 곳 | **서버 쪽 저장소** (메모리 · Redis) | **토큰 자체** (서버는 서명만 검사) |
| 서버를 늘리면 | 모든 서버가 같은 저장소를 봐야 함 → Redis (4교시) | 서명 검사 열쇠만 있으면 어느 서버든 확인 |
| 강제로 로그아웃시키기 | 저장소에서 지우면 끝 | 어렵다 — **만료 시간**까지 유효 |
| 비유 | 물품 보관소 **번호표** | 주민센터 **도장 찍힌 확인서** |

> [!IMPORTANT]
> **어느 쪽도 정답은 아니다**
>
> 세션은 통제하기 쉽고, 토큰은 확장하기 쉽습니다. 그래서 현업은 **수명이 짧은 접근 토큰**(예: 15분)과 **수명이 긴 갱신 토큰**을 함께 써서, 토큰의 확장성과 세션의 통제력을 섞습니다. 토큰이 짧게 살수록 도난당했을 때 피해도 짧습니다.

## JWT 읽기

JWT(JSON Web Token)는 점(`.`)으로 나뉜 세 부분입니다. 각 부분은 **암호화가 아니라 인코딩**(Base64URL)이라 누구나 풀어 볼 수 있습니다.

```text
eyJhbGciOiJSUzI1NiJ9                                   ← 헤더
.eyJzdWIiOiJ1c2VyLTQyIiwicm9sZSI6ImN1c3RvbWVyIiwi…    ← 내용(클레임)
.kX9…Qw                                                ← 서명
```

풀어 보면 앞의 두 부분은 이렇습니다.

```json
{ "alg": "RS256" }
{ "sub": "user-42", "role": "customer", "exp": 1795600000 }
```

| 부분 | 뜻 |
|---|---|
| 헤더 `alg` | 어떤 방식으로 서명했나 |
| `sub` (subject) | 이 토큰의 주인 — **누구인가** |
| `role` 등 | 이 사람에 대한 주장(claim) — 인가 판단에 쓴다 |
| `exp` (expiration) | 만료 시각(1970년부터 센 초) |
| 서명 | 발급자의 비밀 열쇠로 만든 값. **한 글자라도 바꾸면 검사에 실패** |

> [!WARNING]
> **서명은 '변조 방지'이지 '비밀 보장'이 아니다**
>
> JWT는 누구나 내용을 읽을 수 있습니다. 그러니 **비밀번호 · 개인정보를 토큰에 넣으면 안 됩니다.** 서명이 보장하는 것은 "내용이 발급 뒤 바뀌지 않았다"는 것뿐입니다. 그리고 토큰을 훔친 사람은 만료 전까지 **주인 행세**를 할 수 있으므로, 토큰은 1일차에 약속한 대로 **화면 · 채팅 · 저장소에 노출 금지**입니다.

## 남의 신원을 빌려 쓰기 — OAuth 2.0과 OIDC

"GitHub로 로그인", "Google로 계속하기" 버튼은 내 비밀번호를 그 서비스에 주지 않고 로그인하게 해 줍니다.

```text
① 사용자 ──"GitHub로 로그인"──▶ 서비스
② 서비스 ──사용자를 보냄──▶ GitHub 로그인 화면 (비밀번호는 GitHub에만 입력)
③ GitHub ──"이 서비스에 이름·이메일 읽기를 허락할까요?"──▶ 사용자: 허락
④ GitHub ──일회용 코드──▶ 서비스 ──코드를 토큰으로 교환──▶ GitHub
⑤ 서비스는 받은 토큰으로 허락된 범위(scope)만 사용
```

| 표준 | 하는 일 | 비유 |
|---|---|---|
| **OAuth 2.0** | **권한 위임** — "이 앱이 내 대신 저장소 목록을 읽어도 된다" | 대리인에게 주는 **위임장** (범위 · 기한이 적힘) |
| **OIDC** (OpenID Connect) | OAuth 위에 **신원 확인**을 얹음 — ID 토큰(JWT)으로 "이 사람은 누구다" | 위임장에 **신분 확인서**를 붙임 |

## 이 과정에서 다시 만나는 곳

| 주차 | 장면 | 오늘 개념 |
|---|---|---|
| 2주차 1일차 | `gh auth login` — 브라우저에서 승인하고 토큰을 받음 | OAuth 2.0 |
| 3주차 2일차 | GitHub Actions가 GHCR에 이미지를 올릴 때 쓰는 `GITHUB_TOKEN` | 수명이 짧은 토큰, 범위(permissions) |
| 4주차 5일차 | Pod가 API 서버에 내미는 **ServiceAccount 토큰** · RBAC | JWT 인증 + 역할 기반 인가 |
| 5주차 1일차 | `aws login` — 브라우저 로그인 후 임시 자격 증명 | 짧은 토큰 |
| 5주차 3일차 | GitHub Actions가 **비밀번호 없이** AWS 역할을 맡음 | **OIDC** — ID 토큰을 AWS가 검사 |

> [!IMPORTANT]
> **흐름은 하나다**
>
> "오래 사는 비밀(비밀번호, Access Key)을 여기저기 두지 말고, **확인된 신원으로 짧게 사는 토큰을 받아 쓴다.**" 5주 동안 이 방향으로 점점 옮겨 갑니다.

## API를 다시 보내도 안전한가 — 멱등성

네트워크는 실패합니다(3일차). 응답을 못 받으면 클라이언트는 **다시 보냅니다**. 그때 두 번 처리되면 안 되는 요청이 있습니다.

| 메서드 | 두 번 보내면 | 멱등(idempotent)? |
|---|---|---|
| `GET /orders/7` | 같은 주문을 두 번 읽음 | ✓ |
| `PUT /orders/7` (전체 교체) | 같은 내용으로 두 번 덮어씀 — 결과 같음 | ✓ |
| `DELETE /orders/7` | 이미 지워진 것을 또 지움 — 결과 같음 | ✓ |
| `POST /orders` (새로 만들기) | **주문이 두 개** 생김 | ✗ |

결제처럼 두 번 일어나면 안 되는 `POST`에는 클라이언트가 **멱등 키**(`Idempotency-Key: 7f3c…`)를 붙이고, 서버는 같은 키의 두 번째 요청에 **첫 결과를 그대로 돌려줍니다.** 3주차 2일차의 "재시도"를 안전하게 만드는 장치입니다.

> **📘 그 밖에 좋은 API의 습관**
>
> | 습관 | 예 | 이유 |
> |---|---|---|
> | 버전을 주소에 | `/api/v1/products` | 바꿔도 옛 클라이언트가 안 깨진다 (3주차 1일차) |
> | 목록은 나눠서 | `?limit=20&cursor=…` | 100만 건을 한 번에 보내지 않는다 |
> | 에러도 형식 있게 | `{"error":"OUT_OF_STOCK","message":"…"}` | 사람과 프로그램이 모두 읽는다 |
> | 너무 많이 부르면 **429** | `Retry-After: 30` | 6교시 폭주 트래픽에서 서버를 지킨다 |

> **🎓 학술 노트 — 위임의 표준화 (RFC 6749, 2012)**
>
> OAuth 이전에는 다른 서비스가 내 메일 연락처를 가져오려면 **내 메일 비밀번호를 그 서비스에 직접 입력**해야 했습니다. 이 방식은 비밀번호가 여러 곳에 퍼지고, 권한을 일부만 주거나 나중에 거둘 수가 없었습니다. 2007년 트위터 · 구글 등의 개발자들이 모여 만든 OAuth는 2012년 IETF의 **RFC 6749(OAuth 2.0)**로 표준이 되었고, **"비밀번호 대신 범위와 기한이 정해진 토큰을 준다"**는 생각을 웹 전체에 퍼뜨렸습니다. 2015년의 **RFC 7519(JWT)**는 그 토큰을 서명된 JSON으로 주고받는 형식을 정했습니다. 보안 연구자들은 이후 잘못된 구현이 낳는 취약점(리다이렉트 주소 검증 누락 등)을 꾸준히 보고했고, 그 교훈을 모은 보안 모범 사례가 RFC 9700(2025)으로 정리되었습니다.
>
> - Hardt, D. (Ed.). (2012). *RFC 6749: The OAuth 2.0 Authorization Framework*. IETF.
> - Jones, M., Bradley, J., & Sakimura, N. (2015). *RFC 7519: JSON Web Token (JWT)*. IETF.

> **📈 트렌드 — 비밀번호 없는 로그인**
>
> 사람 쪽에서는 **패스키(passkey)**가 비밀번호를 대신하고 있습니다. 패스키는 FIDO2/WebAuthn 표준으로, 휴대폰이나 노트북에 저장된 **개인 열쇠로 서명**해 로그인하므로 피싱 사이트에 비밀번호를 빼앗길 일이 없습니다. 2025~2026년에 GitHub, Google, Apple, Microsoft 등 주요 서비스가 패스키를 기본 선택지로 밀고 있습니다. 기계 쪽에서는 5주차에 볼 **OIDC 연동**(CI가 클라우드 열쇠 없이 역할을 맡음)이 같은 방향입니다 — 사람이든 기계든 **오래 사는 비밀을 없애는 쪽**으로 갑니다.

## 정리

- **인증**은 누구인가(실패 401), **인가**는 무엇을 해도 되나(실패 403)입니다.
- 세션은 상태를 **서버 저장소**에, 토큰은 **토큰 자체**에 둡니다. 현업은 짧은 접근 토큰 + 갱신 토큰을 섞어 씁니다.
- JWT는 누구나 읽을 수 있고, 서명은 **변조 방지**만 보장합니다. 비밀을 넣지 말고, 노출하지 않습니다.
- OAuth 2.0은 **권한 위임**, OIDC는 그 위의 **신원 확인**입니다. 이 과정에서 `gh auth login`부터 5주차 OIDC까지 계속 나옵니다.
- 다시 보내도 결과가 같은 요청이 **멱등**입니다. 결제 같은 `POST`에는 멱등 키를 씁니다.

> **✅ 확인 문제**
>
> 1. 로그인은 됐는데 관리자 페이지에서 거절당했습니다. 상태 코드는 401과 403 중 무엇이 맞나요?
> 2. 서버를 3대로 늘렸더니 로그인이 자꾸 풀립니다. 세션 방식이라면 무엇을 고쳐야 하나요?
> 3. JWT의 내용에 사용자 비밀번호를 넣어도 되나요? 이유는?
> 4. "이 앱이 내 대신 GitHub 저장소 목록을 읽어도 된다"를 표준화한 것은?
> 5. `POST /payments`를 네트워크 오류로 다시 보낼 때 결제가 두 번 되지 않게 하는 장치는?
>
> <details><summary>정답</summary>
>
> 1. 403 — 누구인지는 알지만 권한이 없습니다.
> 2. 세션을 각 서버 메모리가 아니라 모든 서버가 함께 보는 저장소(예: Redis)에 둡니다.
> 3. 안 됩니다. JWT는 인코딩일 뿐 암호화가 아니어서 누구나 읽을 수 있습니다.
> 4. OAuth 2.0
> 5. 멱등 키(`Idempotency-Key`) — 같은 키의 두 번째 요청에는 첫 결과를 돌려줍니다.
>
> </details>
